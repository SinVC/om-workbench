## 一、硬性执行红线
1. **只审不改**：全程保持工作区只读，严禁修改任何业务源码、配置或设计文档；可运行只读的静态检查、类型检查与测试命令获取真实反馈。
2. **事实核查（零幻觉门禁）**：下达任何关于框架、编译器、数据库驱动或第三方库“默认行为缺失/不生效”的结论前，必须核查项目锁文件版本、`build` 脚本或本地依赖源码予以证实；若受环境限制无法核实，必须显式标注“待验证假设”，严禁把猜测当成缺陷。
3. **阶段边界对齐**：先从文档识别项目演进阶段（如 P0/P1/P2 或 MVP/远期），仅按当前所处阶段的契约基线判定功能缺失；对明确规划在后续阶段的能力，仅评估当前结构是否阻碍未来接入，不得误报为漏实现。

## 二、五维评审清单

### 1. 契约一致性与文档自洽性
- **代码 ↔ 契约**：按“顶层导航 → 共享契约 → 模块下钻文档”核对职责边界、接口签名、错误码语义、事件时机、安全权限与验收口径。
- **文档 ↔ 文档 / 配置**：指出顶层约束、子模块文档与工程配置文件之间相互冲突的条款，或已失效/未生效的残留配置。

### 2. 运行时动态、并发安全与优雅退化
- **高频路径与线程模型**：排查高频事件（UI 交互、监听轮询、流式回调）是否直连高代价操作（同步刷盘、全量序列化、跨进程广播），以及同步回调与异步运行时混用是否阻塞主线程或引发死锁。
- **边界与崩溃防御**：检查浮点精度/整数溢出、空集合、并发竞争条件、事务部分失败后的外部副作用（如临时文件/孤儿资源）清理。
- **故障退化**：区分核心用户数据与非关键运行时缓存——非核心缓存损坏或缺失时是否能安全降级恢复，而非阻断系统启动。

### 3. 测试有效性审计
- 执行项目的静态检查与现有测试套件。
- 审视测试脚手架是否自建了与生产环境不一致的初始化路径、连接参数或权限上下文，指出“单测通过但生产路径未被覆盖”的盲区。

### 4. 反过度设计与过度防御审视（做减法）
- **冗余锁与间接层**：识别跨正交子系统的粗粒度全局锁、无实际收益的双重映射/包装层、前端或上层根本未使用的重型插件/依赖。
- **重叠与误伤性防御**：识别已被底层机制（参数化绑定、类型系统、操作系统规范化路径）天然保障却仍在业务层重复堆砌的校验，尤其是误伤合法业务输入或成倍放大内存/CPU 开销的防御逻辑。

### 5. 模块结构与演进重构评估
- **关注点分离（SoC）**：排查上帝函数/巨型分发器、跨层散落的工具/校验逻辑、违背框架原生强类型惯用法的手动胶水代码。
- **状态单一事实源**：排查同一业务或配置状态是否分散在多个存储实体中双向互写、缺乏单一所有权。
- **演进就绪度**：评估当前目录与模块拓扑在接入下一阶段规划特性时的修改爆炸半径，给出最小必要的结构重构方向。

## 三、输出格式要求
1. **总体基线评估**：简述当前阶段契约达成度、架构亮点及静态检查/单测实跑结果。
2. **分级缺陷清单**（按 `Critical` / `High` / `Medium` / `Low` 排序）：每项必须包含【精确文件与行号】、【触发路径与实际影响】、【对照契约/源码依据】、【最小修复方向】。
3. **减法清单（过度设计/过度防御）**：说明每一处冗余设计的本意、带来的副作用及精简方案。
4. **结构重构建议与路线图**：按“当前阶段必改缺陷”与“下一阶段前置重构”给出优先级矩阵，避免一步到位的过度重构。
