# 技术栈选型与关键架构决策

本文档固化个人自定义工作台的技术选型矩阵及核心架构取舍依据，统领 Tauri 宿主与前端工作台双端的技术演进方向。

---

## 一、双顶层域技术选型矩阵

### 1. 顶层逻辑一：Tauri 桌面宿主（`tauri-host`）

| 技术层次 | 选型结果 | 架构职责与选型理由 |
| :--- | :--- | :--- |
| **桌面应用框架** | **Tauri 2 (Rust)** | 复用操作系统原生 WebView（Windows 端为 WebView2），安装包轻量，兼具跨平台（Windows / macOS）演进潜力与严密的 Capabilities 权限模型。 |
| **外置资源挂载** | **Tauri 自定义协议 / 本地目录加载** | 突破默认 `frontendDist` 静态内嵌限制，直接挂载客户本机可编辑的工作台构建目录，无需额外部署静态网站或常驻本地 HTTP 服务进程。 |
| **结构化持久化** | **SQLite（官方 SQL 插件 + 自定义命令）** | 本地单文件关系型存储，摆脱浏览器缓存回收（Eviction）风险，支撑 JSON 扩展字段检索、跨表查询与多写原子事务。 |
| **窗口状态管理** | **Tauri Window API + 按形态独立持久化** | 支持运行时免编译动态切换窗口形态、尺寸与屏幕坐标，分别记忆侧栏与面板的窗口边界；无标题栏窗口由页面调用标准窗口操作接口。 |
| **原生网络客户端** | **Tauri HTTP Client 插件（底层 `reqwest`）** | 在原生层发起外部 API 请求，天然绕过 WebView 的浏览器跨域（CORS）限制，并承载宿主侧超时控制与凭据安全注入。 |

### 2. 顶层逻辑二：React + TypeScript + Vite 工作台页面（`web-workbench`）

| 技术层次 | 选型结果 | 架构职责与选型理由 |
| :--- | :--- | :--- |
| **视图框架与语言** | **React + TypeScript** | 适合将数十个业务模块按数据、行为与展示分层拆解；静态类型声明（`.d.ts`）可显著降低本机编码 Agent 调用 SDK 时的幻觉与试错成本。 |
| **构建与热更工具** | **Vite** | 极速编译 TSX 与样式资源，将所有第三方依赖打包为离线自包含的静态 HTML/CSS/JS 产物，配合监听模式支撑“Agent 改码 → 自动构建 → 窗口刷新”闭环。 |
| **样式与自适应** | **CSS 主题变量 + 容器查询（`@container`）** | 通过统一语义令牌（Design Tokens）驱动深浅色与视觉换肤；利用容器查询使组件按所在区域实际宽度自适应重排，兼容窄侧栏与宽面板。 |
| **基础 UI 原语** | **shadcn/ui** | 以项目源码形态直接分发而非黑盒 npm 包，本机 Agent 可直接阅读与改写组件结构及样式，灵活度高且无私有抽象束缚。 |
| **复杂表格引擎** | **TanStack Table** | 无预设界面的无头表格引擎（Headless UI），负责排序、多维筛选与分页状态计算，由工作台补齐统一视觉外观与行内编辑交互。 |
| **日历排程组件** | **FullCalendar（标准版）** | 承接日、周、月视图渲染与日程拖拽交互，免除手写复杂日历网格与跨天排布算法的维护负担。 |
| **统计可视化** | **Recharts + 轻量内联 SVG** | 复杂多维折线、柱状、饼图采用本地打包的 Recharts；进度环、微型趋势线与 365 格热力图等轻量图形可直接采用内联 SVG 渲染。 |

## 二、关键架构决策记录

### 1. 桌面容器取舍：选择 Tauri 2 + SQLite，放弃纯 PWA、Electron 与纯 C# WebView2
- **对比纯 PWA + IndexedDB**：标准 PWA 首次安装与更新依赖 HTTPS 静态站点托管，无法仅靠双击本地文件完成标准安装，且浏览器 IndexedDB 存在被用户清理或触发系统存储回收的风险；更重要的是，PWA 难以直接挂载客户本机可持续编辑的外部工作区目录。本产品明确要求“安装包开箱即离线运行、本机文件长期可靠保存、本机 Agent 直接改本地目录”，故以 Tauri 2 + SQLite 为唯一主架构。
- **对比 Electron**：工作台核心为本地数据管理与多视图渲染，无需强绑定 Node.js 原生桌面生态，Tauri 复用系统 WebView 可大幅缩减分发体积与内存开销（Windows 安装器负责检测并按需补齐 WebView2 Runtime）。
- **对比 C# + WebView2**：C# 方案仅限 Windows 平台；Tauri 2 在具备同等本地目录渲染能力的同时保留跨平台扩展架构，长期维护收益更高。

### 2. 交付边界决策：预编译运行器固定，前端源码外置可编辑
桌面端原生编译环境（Rust 工具链与系统 SDK）严禁传导至终端用户。平台方负责编译并分发稳定的 Tauri 运行器；客户侧仅保留工作台前端工程与配置文件。日常增删模块、调整布局、换肤与配置外部接口均在前端构建管线与运行时配置内闭环，彻底免除宿主重编译。

### 3. 前端技术路径收敛：以 React + Vite 为统一主线，保持宿主接口原生 JS 兼容
同时维护“React 组件模板”与“纯原生 HTML/JS 模板”两套完整体系会导致研发与测试成本翻倍。系统确立 **React + TypeScript + Vite** 为标准交付主路径，由配套脚本封装构建与刷新动作；同时，Tauri 宿主启用全局 API 注入，使底层 `workbench.*` 通信契约保持对原生 JavaScript 的直接可调用性，不堵死极简静态页接入的底层通道。

### 4. Agent 时代组件策略：重数据契约与稳定 SDK，轻黑盒业务组件库
面向先进编码 Agent 定制个人工作台的场景，预先构建庞大、参数封闭的私有业务组件库属于过度设计——Agent 阅读专有组件文档、理解属性约束及绕过样式限制所消耗的上下文 Token 与调试轮次，往往高于直接编写简单视图。因此：
- **必须统一收敛的层**：底层数据存取、附件管理、事务一致性与跨视图共享的核心领域规则（如重复任务推算）。
- **保持开放灵活的层**：简单列表、卡片、进度条等界面外观交由 Agent 自由生成或基于 **简短、可读、可直接复制修改的源码示例** 改造；仅在日历、复杂表格、统计图表等高复杂度交互上引入成熟开源底座。
- **演进前提**：首版暂缓建设重型组件库，待积累真实使用样本并通过空白开发与示例改造的 A/B 效能对比后，再将高频重复编写的逻辑下沉封装。

### 5. 工程规范基线
- **仓库拓扑**：根仓同时是 npm workspaces 与 Cargo workspace 的根，成员仅为 `web-workbench` 与 `tauri-host` 两个顶层域；跨域共享的工程配置（TypeScript 基线、代码检查、格式化）统一收敛在根仓，成员只做继承与少量覆盖。
- **包管理**：选用 npm，并以根目录 `package-lock.json` 作为唯一锁文件。理由是 npm 随 Node.js 自带，客户本机仅需安装 Node.js 即可构建工作台，不再引入额外的包管理器依赖。
- **TypeScript 基线**：前端源码与工程配置文件（Vite、ESLint 等）一律使用 TypeScript 编写，不新增 JavaScript 源文件。全仓统一开启 `strict` 及索引访问检查，采用 `bundler` 模块解析且不产出编译文件；类型检查（`tsc`）与 Vite 构建是两个独立的环节，构建不替代类型检查。
- **代码检查与格式化**：前端采用 ESLint flat config（typescript-eslint + React Hooks 规则）负责代码质量，Prettier 独占格式化职责，二者规则互不重叠；宿主 Rust 代码采用 `rustfmt` 与 `clippy`。

### 6. 离线打包与开源许可证治理
所有引入的第三方前端库、图标与字体均在 Vite 构建阶段静态打包进本地产物，严禁产生运行时外部网络请求。[前端依赖清单](../../web-workbench/THIRD_PARTY_NOTICES.md)记录直接运行时依赖及许可证，版本以根锁文件为准。FullCalendar 仅启用 MIT 许可的标准版能力，严禁在未获取商业授权前引入其 Premium 专有插件。
